# M4.1 Runtime Cutover - Reforged Backend Chat Completions

> Status: completed for the M2.5 mainline baseline on `reforge/m4.1-runtime-cutover` (2026-06-13).
> Scope: ordinary single-player chat generation now uses the Reforged backend path first, while M4 multiplayer rooms remain a spike-level foundation for the M4主体.

## Product Direction

M4.1 is the first runtime cutover step after ADR-005. Reforged's end state is a server deployment made of:

- the new Vue frontend in `app/`;
- the new Reforged backend in `reforged-server/`;
- compatibility with SillyTavern asset formats and behavior semantics.

Compatibility means ST character cards, world info/worldbook data, OpenAI preset and `prompt_order` data, regex rules, and other assets should keep their user-facing meaning. It does not mean keeping the old ST DOM, jQuery UI assumptions, or backend route structure as the normal runtime path.

This supersedes the older PRD v0.2 assumption that the backend is "mostly unchanged" for the M4 runtime path. That assumption was already revised by `docs/refactor/M2-persistence-compat-plan.md` and accepted in ADR-005.

## Runtime Paths

### Single-Player Chat

Ordinary `/chat` generation can now use:

1. `reforged-backend`: the preferred server-hosted path. The frontend sends an OpenAI-compatible request to `POST /api/reforged/chat/completions`; the Reforged backend proxies provider traffic and returns OpenAI-compatible JSON or SSE chunks.
2. `browser-direct`: browser-to-provider fetch for providers that support CORS.
3. `legacy-proxy`: the old SillyTavern backend proxy compatibility bridge.
4. `auto`: prefer Reforged backend, then browser-direct where applicable, with legacy proxy kept as a compatibility fallback.

The frontend still constructs chat messages from the contract layer and normalizes OpenAI-compatible SSE through the shared parser in `app/src/engine-adapter/openAiSseStream.ts`.

### Multiplayer Rooms

M4 room behavior remains server-authoritative:

- room create/join/key submission still use `reforged-server`;
- participants continue to own their own provider key;
- any participant may trigger generation;
- room event logs and WebSocket payloads expose only public provider metadata such as `keyRef`, `baseUrl`, `model`, and masked labels.

M4.1 does not replace the room protocol with the single-player endpoint. The new endpoint gives single-player chat the same Reforged backend runtime foundation that rooms already use.

M4 room work is still deliberately unfinished after this cutover. The spike proves room create/join/key submission, WebSocket broadcast, and participant-owned generation, but the M4主体 still needs durable room/event storage, streaming `generation.chunk` events, account or stronger identity design, host controls, rate limits, TLS deployment guidance, and provider target allowlisting for public deployments.

## Credential Rules

API keys are runtime secrets. They must not appear in:

- Pinia serializable state;
- action payloads that may be recorded or replayed;
- WebSocket broadcasts;
- room event logs;
- tests snapshots;
- console logs;
- provider error bodies surfaced to the user.

For single-player chat, the browser may submit a key only as transient request material, preferably as an `Authorization: Bearer ...` header to the Reforged endpoint. The backend may use it for the provider request or an in-memory vault, but it must not persist or echo it.

For multiplayer rooms, participant keys remain in the backend transient vault keyed by participant id. The client-provided provider config in generation requests is advisory/public only; the backend authorizes generation with the WebSocket participant id and that participant's vault entry.

## Asset Compatibility Route

Runtime cutover is deliberately smaller than full asset-editor parity:

- character card V2/V3 import remains a frontend compatibility parser concern;
- world info/worldbook import remains compatible at the contract/parser level;
- OpenAI presets and `prompt_order` continue to shape `messages` and sampling before runtime dispatch;
- regex compatibility is still a future compatibility layer, not part of this endpoint.

The Reforged backend should receive normalized runtime requests, not old ST UI state.

## Verification

Required automated gates for this baseline:

```bash
node --test reforged-server/server.test.js
cd app && npm run type-check
cd app && npm run test
cd app && npm run build
```

M2.5 completion record (2026-06-13):

- `node --test reforged-server/server.test.js`: 9/9 passing.
- `cd app && npm run type-check`: passing.
- `cd app && npm run test`: 256/256 passing.
- `cd app && npm run build`: passing.
- Manual smoke reported passing for single-player `8787` generation and two-browser room create/join/broadcast.

Manual smoke without the legacy ST backend:

1. Start the Reforged backend:
   ```bash
   REFORGED_GENERATION_MODE=stub node reforged-server/server.js
   ```
2. Start the Vue app:
   ```bash
   cd app && npm run dev
   ```
3. Open `http://localhost:5173/#/chat`.
4. Configure connection transport as Reforged backend and send a normal single-player chat message.
5. Confirm a streaming or stub assistant reply appears without the old ST `8000` server running.
6. In two tabs, create/join a multiplayer room, broadcast a user message, submit participant keys, and trigger generation from either participant.

## Non-Goals

- No changes to `public/` legacy ST source.
- No call to DOM-heavy `Generate()` or old jQuery DOM paths.
- No new unapproved package dependencies in this cutover; the approved M2 dependencies remain `three`, `@types/three`, and `fake-indexeddb`.
- No durable room store or account system yet.
- No full rewrite of asset editors in this milestone.
