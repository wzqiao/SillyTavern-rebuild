# M2.5 Public Launch Checklist

> Date: 2026-06-13
> Target: same-domain public beta for the M2.5 mainline baseline on `st.rua.chat`.
> Branch/tag baseline: `reforge/main` / `m2.5-mainline-complete`.

## Launch Shape

Today ships the M2.5 usable beta, not the full M4 multiplayer product.

- Public domain with HTTPS.
- One domain serves the Vue app and proxies `/api/reforged/*` to `reforged-server`.
- `REFORGED_TOKEN` protects backend routes and room WebSocket upgrades. On the public same-domain deployment, inject it at the reverse proxy so ordinary users do not type or see it.
- App data persists as JSON under `reforged-server/data/`.
- Room state and participant provider keys are still in memory and are lost on backend restart.

## What `REFORGED_TOKEN` Means

`REFORGED_TOKEN` is a temporary shared server password for this beta. The backend requires it on protected HTTP routes and WebSocket upgrades.

For local smoke testing, a throwaway value such as `dev-token` is fine. For anything reachable from the public internet, use a long random value even if another project-level unified auth layer will replace this later.

Use a long random value, for example:

```bash
openssl rand -base64 32
```

Do not commit the real token to git, docs, screenshots, issue comments, or frontend build-time constants. For `st.rua.chat`, configure the token in Nginx/Caddy and inject `X-Reforged-Token` while proxying `/api/reforged/*`.

Future auth note: `REFORGED_TOKEN` is intentionally a stopgap. When the shared rua.chat auth gateway is ready, replace or wrap this backend token check with that unified identity/session layer and keep raw provider keys out of logs, broadcasts, and persisted room state.

## Required DNS / Reverse Proxy Decision

DNS target:

```text
https://st.rua.chat
```

Use same-domain routing:

```text
https://st.rua.chat/               -> app/dist static files
https://st.rua.chat/api/reforged/* -> http://127.0.0.1:8787/api/reforged/*
```

With same-domain hosting, the frontend defaults to the current origin on public hosts. On localhost it still defaults to `http://127.0.0.1:8787` for development.

## Local Smoke Before Server Upload

Fast local test with the dev server:

```bash
# terminal A
REFORGED_TOKEN=dev-token \
REFORGED_ALLOWED_ORIGIN=http://localhost:5173,http://127.0.0.1:5173 \
REFORGED_GENERATION_MODE=stub \
node reforged-server/server.js

# terminal B
cd app
npm run dev
```

Open `http://localhost:5173`, go to Settings, set:

- Reforged server URL: `http://127.0.0.1:8787`
- Reforged server token: `dev-token`

Reload once, then confirm storage switches to Reforged backend and a stub chat reply works. `npm run preview` does not provide the same `/api/reforged/*` reverse proxy as Nginx, so use the explicit server URL above for local testing unless you also set up local Nginx/Caddy.

## Backend Runtime

Run the backend on loopback behind the reverse proxy:

```bash
export REFORGED_TOKEN="<long-random-token>"
export REFORGED_ALLOWED_ORIGIN="https://st.rua.chat"
export REFORGED_GENERATION_MODE="proxy"
export REFORGED_PORT="8787"
node reforged-server/server.js
```

Notes:

- Do not set `REFORGED_ALLOWED_ORIGIN=*` for public launch.
- Keep the backend bound to `127.0.0.1`; expose it through the HTTPS reverse proxy.
- `REFORGED_GENERATION_MODE=stub` is only for smoke tests without real provider calls.

## Caddy Example

```caddyfile
st.rua.chat {
  root * /absolute/path/to/SillyTavern/app/dist
  encode gzip zstd
  file_server

  reverse_proxy /api/reforged/* 127.0.0.1:8787 {
    header_up X-Reforged-Token "{env.REFORGED_TOKEN}"
  }
}
```

## Nginx Example

```nginx
server {
    server_name st.rua.chat;

    root /absolute/path/to/SillyTavern/app/dist;
    index index.html;

    location /api/reforged/ {
        proxy_pass http://127.0.0.1:8787/api/reforged/;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header X-Reforged-Token "<same-long-random-token-as-backend>";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

## Browser Smoke Test

1. Open `https://st.rua.chat`.
2. Leave Settings -> Reforged server advanced override empty; same-domain hosting uses `https://st.rua.chat` automatically and the reverse proxy injects the server token.
3. Reload once so app persistence can re-probe the backend through the reverse proxy.
4. Confirm the storage status shows Reforged backend.
5. Go to Connection, set provider base URL, model, and provider API key.
6. Fetch models or test connection. In `auto` or `reforged-backend` transport this uses `POST /api/reforged/models`, so provider CORS does not block the model list.
7. Import a character card.
8. Send a chat message and confirm the reply streams through `reforged-backend`.
9. Refresh the page and confirm chat/character data remains.
10. Open a second browser profile and confirm shared app data is visible while provider API key must be entered locally.
11. Create a room in one browser, join it from the second browser, and confirm message broadcast works.

## Known Launch Limits

- No account system yet.
- Room state is not durable across backend restarts.
- No host moderation surface yet.
- No rate limiting yet.
- Provider target allowlisting/private-IP blocking is not implemented yet; keep this beta private or token-gated.
- `REFORGED_TOKEN` is temporary; replace it with the rua.chat unified auth integration after this beta is online.
- Users must protect their own provider API keys. Runtime keys are not committed or broadcast, but they are still sensitive local/browser input.

## Rollback

Keep the previous deployment directory or release tag available. To roll back:

1. Stop the backend process.
2. Restore the previous `app/dist` directory or checkout the previous tag.
3. Restart the previous backend command.
4. Keep `reforged-server/data/` backed up before replacing deployments.
