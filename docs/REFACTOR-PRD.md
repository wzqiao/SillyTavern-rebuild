| 决策点 | 结论 |
|--------|------|

---

## 1. 背景与动机

**痛点(实测 + 代码佐证):**
- **信息过载**:`index.html` 8200 行、40 个抽屉、几百个选项一次性平铺,无渐进式披露。
- **无移动适配**:桌面 jQuery 浮窗/抽屉范式,手机端割裂。
- **架构陈旧**:`script.js` 1.2 万行"上帝文件"、全局可变状态、被 93 个文件依赖。
- **"原始感"**:外壳过时(2022 前端范式),并非功能落后。

**价值主张**:把"优秀的引擎"从"过时的外壳"里解放出来——做一个 **好用、现代、移动友好、可联机** 的角色扮演前端。

---

## 2. 定位与目标用户
- **定位**:SillyTavern 的 **hard fork**,独立演进;仅在上游有重大功能时手动评估移植。
- **目标用户**:**新手(首要)**——开箱即玩、渐进式披露;**老玩家**——高级模式保留全部深度。

---

## 3. 设计原则
1. **渐进式披露**:简单 / 高级双模式,默认极简。
2. **全端响应式 + 移动优先**:一套代码适配桌面/手机,触控友好。
3. **保留引擎、重做外壳**:AGPL 下复用 ST 引擎,集中火力重做 UI/UX。
4. **接口先行、模块解耦**:为多 agent 并行开发服务。
5. **生态继承**:能导入现有角色卡(V2/V3)与世界书。

---

## 4. 技术架构

### 4.1 总体
- **后端**:复用 ST 后端(Express,AGPL)——API 代理、文件存储、tokenizer。基本不动。
- **前端**:全新 SPA,**Vue 3 + TypeScript + Vite + Pinia + Vue Router + Tailwind CSS**。
  - 响应式:Tailwind 断点 + 移动优先布局;桌面增强(多栏)、移动折叠(抽屉/底栏)。

### 4.2 与 ST 引擎的关系(关键)
- ST"引擎"(`Generate`、世界书、宏、STScript、各家 API 适配)**大部分在前端 JS**;后端主要是代理 + 存储。
- **复用方式**:借鉴酒馆助手,新前端通过 **external import**(`@sillytavern/*` 别名)复用 ST 引擎模块,只重写 UI。
- ⚠️ **关键技术风险**:`script.js` 把引擎逻辑与 jQuery DOM 缠在一起,引擎函数常假设特定 DOM 存在。新 UI 换掉 `index.html` 后,这些 DOM 不在 → 引擎可能崩。
  - **应对**:**M0 架构验证 spike** 先验证(见 §7);可能需"隐藏 ST DOM 兼容层"或把引擎逐步剥离为 headless 适配层。

### 4.3 分层
```
backend (复用 ST, AGPL)
   ▲ HTTP
engine-adapter   ← 桥接 ST 引擎为干净接口(隔离 §4.2 风险)
   ▲
stores (Pinia)   ← 应用状态(取代散落的全局 export let)
   ▲
services         ← 业务逻辑
   ▲
ui (组件库 + 页面)
```

## 5. 功能范围

### 5.1 MVP(M1)= 最小垂直切片
- 配置并连接一个 LLM API(先 1–2 家,如 OpenAI 兼容)
- 导入 / 选择角色(支持 V2/V3 角色卡)→ 进入聊天
- 基础聊天:发送、流式接收、swipe、编辑、删除
- 全端响应式可用
- 极简设置(高级参数收起)

### 5.2 二期及以后
- 渐进式披露的完整设置体系;世界书编辑器现代化;群聊
- **内置功能**(❓优先级,候选):脚本运行时(酒馆助手核心)、变量、正则、楼层增强、主题/美化(cocktail 类)
- **联机**:**世界书房间**——同一世界观多人联机 + 内容分享。**当前仅在架构层预留接口,不实现。**

## 6. 模块分解与多 Agent 并行开发(worktree)

### 6.1 并行开发协议
1. **接口先行**:模块先定 TS 接口契约,评审通过才并行实现。
2. **一模块 = 一 worktree = 一 agent**:低耦合,减少冲突。
3. **架构未定型前不大规模并行**:M0 用单/少 agent 钉死接口;M2+ 才模块化并行。
4. **共享契约**:`app/src/contracts` 由主干维护,各 worktree 只读依赖。

### 6.2 分支与 worktree 策略
- 主干:`reforge/main`(契约 + 集成)。
- 每模块:`reforge/<module>` 在独立 worktree 开发,定期合回主干。

### 6.3 候选模块(M2+ 并行维度)
| 模块 | 职责 | 主要依赖 | 并行性 |
|------|------|---------|--------|
| `engine-adapter` | 桥接 ST 引擎 | 契约 | 低(地基,先做) |
| `stores` | 状态管理 | engine-adapter 契约 | 中 |
| `ui-kit` | 通用组件库 | 无 | 高(可独立) |
| `chat-view` | 聊天界面 | stores, ui-kit | 中 |
| `character-mgmt` | 角色管理 + 导入器 | stores, ui-kit | 高 |
| `settings` | 设置(渐进披露) | stores, ui-kit | 高 |
| `connection` | API 连接配置 | engine-adapter | 中 |
| `multiplayer` | 联机房间(后期) | stores, 后端扩展 | 独立 |
| `theming` | 主题 / 美化 | ui-kit | 高 |

## 7. 里程碑路线图

### M0 · 架构验证 spike(关键,下一步)
**目标**:用最小代价(允许"脏"代码)验证 §4.2 的核心假设——"新 Vue UI 复用 ST 引擎"到底可不可行。

**验证清单:**
- [ ] A. 新 Vite+Vue 工程能否通过 `@sillytavern/*` alias **external import** ST 引擎模块(`Generate` / `eventSource` / `getContext`)?
- [ ] B. ST 引擎函数在"无完整 ST DOM"下能跑到什么程度?**哪些有硬 DOM 依赖?**(列清单)
- [ ] C. 能否从新 UI 触发一次**真实 LLM 生成 + 流式响应**?
- [ ] D. 能否解析导入一张 V2/V3 角色卡?

**产出**:可行性结论报告 + `engine-adapter` 雏形 + 集成模式决策 + 接口契约草案。
**验收**:在一个新 Vue 页面里,连一个 API、选一张导入的角色卡、发一条消息、拿到流式回复(界面可以丑)。

### M1 · 最小垂直切片
把 M0 的"脏验证"做成像样的产品:§5.1 全部,全端响应式,极简设置。

### M2 · 渐进式 UI 体系 + 核心模块并行
设置 / 角色 / 连接 / 组件库(开闸 worktree 并行)。

### M3 · 内置功能
脚本运行时、变量、正则、主题(❓选哪些)。

### M4 · 联机
世界书房间(范式跃迁,最重)。

## 8. 关键风险
1. **引擎与 DOM 耦合**(§4.2)——M0 必须验证,可能推翻"轻量复用"假设。
2. **数据兼容成本**——角色卡 V2/V3、世界书解析。
3. **上游漂移**——hard fork 后移植上游的成本。
4. **联机是范式跃迁**(本地 → 服务)——已推迟至 M4。
